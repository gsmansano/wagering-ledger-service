## Decisions and notes

- **Mapping (#16).** ORM mappings will be `EntitySchema` files in infrastructure with mapper functions calling `rehydrate`; no decorators on domain classes.
- **Ledger immutability (#17).** A row-level trigger rejects `UPDATE` and `DELETE`, so it holds for any writer. `TRUNCATE` is not blocked, which the test truncate helper relies on.
- **Types (#18).** `uuid` ids and `NUMERIC(19,2)` money. Enum-like columns are `text` with `CHECK` rather than Postgres enum types, so adding a value is a one-line constraint change.
- **Replays (#19).** `wager_transactions.balance_after` stores the balance observed at settlement, because `LOSS` and rejections have no ledger entry to derive it from.
- **Opening (#20).** The opening credit is a real transaction row (`kind = OPENING`, provider `SYSTEM`, external id = wallet id), which settles the M2 open question and keeps the ledger foreign key uniform.
- The reversal uniqueness is a partial unique index over `PROCESSED` reversals only, so a rejected reversal does not block a later valid one. A wallet has at most one `OPENING` row (partial unique index).
- The migration is appended rather than replacing `skeleton_probe`, so databases that already applied the placeholder keep working.
- `reference_attempts` and `reference_next_attempt_at` were added to `wager_transactions` as the retry state of the M5 pending-reference worker (and to back the "due" index); the domain entity does not carry them yet.
- Not enforced in the database by design: `wallet.balance` equal to the latest ledger `balance_after` (checked by reconciliation, M9) and protection against lost updates (locking, M4).
- Unit tests stay next to the code (`*.spec.ts`); integration tests stay in `test/integration/`.
- Git rename detection: files were moved without `git mv` to avoid staging; they appear as renames once staged.

## Decisions and notes

- **Mapping (#21).** The domain classes have private state, so the ORM maps plain row types and the mappers are the only code that knows both shapes. Reads use `refresh: true`; writes are native `insert` and `nativeUpdate`.
- **Transactions (#22).** `UnitOfWork.run` gives the work repositories bound to one transaction; there is no ambient context. `transactional` forks the `EntityManager`, so concurrent runs do not share an Identity Map.
- **Ports (#23).** Only the operations needed now are exposed. Row locking is left to M4, when the concurrency strategy is chosen.
- **Observed balance (#24).** `balance_after` is not part of the `WagerTransaction` entity, whose specified signatures are unchanged. The transaction repository returns `PersistedWagerTransaction { transaction, balanceAfter }`, and `update` takes the balance.
- `Money.toString()` includes the currency, so the mappers store `toJSON().amount`.
- Ledger rows carry no currency; `page` reads it from the wallet with one extra query.
- Ledger paging is keyset on `(created_at, id)`, which is stable under concurrent inserts and uses the `(wallet_id, created_at, id)` index.
- For M4: a unique violation aborts the PostgreSQL transaction, so idempotency may prefer `INSERT ... ON CONFLICT DO NOTHING`; `wallets.update` has no lock or version guard yet; Nest wiring for `UnitOfWork` arrives with the first use case.

## Decisions and notes

- **Concurrency (#25).** Pessimistic row lock per wallet, taken before the balance is read. `CHECK (balance >= 0)` remains the backstop. `version` still increments with the balance but is not used for concurrency control.
- **Idempotency (#26).** `ON CONFLICT DO NOTHING` because a plain unique violation aborts the PostgreSQL transaction. A loser blocks on the winner's uncommitted row, then reads its committed result.
- **CreateWallet (#27).** Optional non-negative `initialAmount`; the spec (§9) creates the `OPENING` transaction only when the amount is greater than zero and does not forbid an empty wallet, so an omitted or explicit zero amount creates a valid empty wallet. This amends decision #20: the `OPENING` row exists only with an opening credit.
- The wallet is opened already holding the amount, so `version` is 1 as in the spec example; the opening ledger entry is built directly from balance 0 instead of through `credit`.
- The `OPENING` transaction uses provider `SYSTEM`, external id = wallet id, idempotency key `opening:<walletId>` and the label `opening` for round and game.
- Only `WalletBalanceChanged` is emitted for the opening; no `WagerTransactionProcessed` event for the internal transaction.
- The HTTP body shape for wallet creation (`initialBalance` object vs. `currency` plus amount) is left to M6.

## Decisions and notes

- **Order and outcomes (#28).** Idempotency insert before the lock, so duplicates of a settled transaction never queue on the wallet lock. `BET`/`WIN` emit `WagerTransactionProcessed` and `WalletBalanceChanged`, `LOSS` only the first, a rejection only `WagerTransactionRejected`.
- **Requests that persist nothing (#29).** Unknown wallet, `OPENING` from outside, wrong player, invalid payload and (until M5) `REFUND`/`ROLLBACK`. `WALLET_NOT_FOUND` stays unused.
- **External id under a new key (#30).** Replay if the payload hash matches, conflict otherwise.
- **Lock level (amends #25).** `FOR UPDATE` deadlocked two concurrent non-duplicates: inserting the transaction row takes a `FOR KEY SHARE` lock on the wallet through the foreign key, and both requests then waited for each other's `FOR UPDATE`. `FOR NO KEY UPDATE` still serializes writers and is compatible with that share lock; the wallet key is never changed. MikroORM has no mode for it, so the lock is a raw statement followed by a refreshed read.
- **Wallet deletion.** The schema blocks hard deletion of any wallet with history (foreign keys and the immutable ledger). Closing an account is designed as a soft `status` checked under the lock; to be described in `ARCHITECTURE.md` (M11).
- Concurrent requests are serialized, not ordered by arrival; ordering is an optimization left to SQS FIFO groups (M7). There is no `lock_timeout` yet; to be considered in M10 together with the lock-conflict metric.
