## Decisions and notes

- **Ledger immutability (#17).** A row-level trigger rejects `UPDATE` and `DELETE`, so it holds for any writer. `TRUNCATE` is not blocked, which the test truncate helper relies on.

## Decisions and notes

- **Order and outcomes (#28).** Idempotency insert before the lock, so duplicates of a settled transaction never queue on the wallet lock. `BET`/`WIN` emit `WagerTransactionProcessed` and `WalletBalanceChanged`, `LOSS` only the first, a rejection only `WagerTransactionRejected`.
- **Requests that persist nothing (#29).** Unknown wallet, `OPENING` from outside, wrong player, invalid payload and (until M5) `REFUND`/`ROLLBACK`. `WALLET_NOT_FOUND` stays unused.
- **External id under a new key (#30).** Replay if the payload hash matches, conflict otherwise.
- **Lock level (amends #25).** `FOR UPDATE` deadlocked two concurrent non-duplicates: inserting the transaction row takes a `FOR KEY SHARE` lock on the wallet through the foreign key, and both requests then waited for each other's `FOR UPDATE`. `FOR NO KEY UPDATE` still serializes writers and is compatible with that share lock; the wallet key is never changed. MikroORM has no mode for it, so the lock is a raw statement followed by a refreshed read.
- **Wallet deletion.** The schema blocks hard deletion of any wallet with history (foreign keys and the immutable ledger). Closing an account is designed as a soft `status` checked under the lock; to be described in `ARCHITECTURE.md` (M11).
- Concurrent requests are serialized, not ordered by arrival; ordering is an optimization left to SQS FIFO groups (M7). There is no `lock_timeout` yet; to be considered in M10 together with the lock-conflict metric.

M5 — Reversals and out-of-order references, in three steps: REFUND and ROLLBACK against a processed reference, parking of reversals whose reference is missing, and the background worker that retries them.

## Completed

- **Step 1 (commit `2908e2a`).** REFUND and ROLLBACK are checked under the wallet lock: same player, wallet, round and currency, a reversible kind, a processed reference, an equal amount and no earlier reversal. Each failure is a persisted rejection with its own failure code. A debiting reversal that would overdraw is rejected as `REVERSAL_WOULD_OVERDRAW`.
- **Step 2 (commit `cae1fbd`).** A reversal whose reference is missing or still in flight is stored as `PENDING_REFERENCE` with a `WagerTransactionPendingReference` event and answers `202`. `ResolvePendingReference` retries one such transaction under the wallet lock through the same apply path as a first delivery, reschedules with exponential backoff and rejects with `REFERENCE_NOT_FOUND` at the last attempt. The apply logic was extracted into `applyUnderLock`, shared by both use cases. `UnsupportedKindError` was removed.
- **Step 3 (uncommitted).** `PendingReferenceWorker` polls due rows with `FOR UPDATE SKIP LOCKED`, claiming and retrying each in one SQL transaction; it is configurable through `PENDING_REFERENCE_*` variables and runs in every instance. Added `bun run poc:reversals`, README section and `.env.example` entries. M5 is ticked in `PLAN.md` and M6 is marked current.

## Decisions and notes

- **Rule 4 (#36).** A transaction is reversed at most once, by any kind. The literal wording ("same kind") would allow a BET to be both REFUNDed and ROLLBACKed; the stricter reading is documented as an added interpretation and enforced by a partial unique index.
- **Overdraw (#37) and reference judgement (#38).** A reversal that would make the balance negative is a final, audited rejection. A reference that exists is judged at first sight; only a missing or in-flight one waits.
- **Retry limit (#39), worker-driven resolution (#40), `202` (#41).** 10 retries, delays of 1 s doubling to a 5 min cap (about 13 minutes in total); no eager wake-up when the reference is processed; the HTTP status stays provisional until M6.
- **Worker locking (#42).** The pending row is locked before the wallet, in every path, so a worker and a direct retry cannot deadlock. After the row lock the status read is authoritative.
- Retry state (`reference_attempts`, `reference_next_attempt_at`) stays in the table and out of the entity, per #10.
- The `OutboxMessage` events written here are not published yet; publication is M8.
- Decision #31's provisional status table now includes `202`; the complete table is M6.

# Session log: 2026-10-16 (eleventh session)

## Objective

M7 — SQS consumer and inbox, in three steps: the message contract and the atomic inbox, the polling consumer with error classification, and graceful shutdown with the PoC.

## Completed

- **Design (decisions #51–#55).** Settled and logged the inbox technique, the error classes, the explicit dead-letter path, the FIFO group key and the consumer concurrency and shutdown behaviour.
- **Step 1 (commit `f66cab4`).** `InboxRepository.insertIfAbsent` (`ON CONFLICT DO NOTHING`). `ProcessWagerTransaction.execute` accepts an optional `inbox: { consumerName, messageId }`: the inbox row is written first, already processed, in the use case's own SQL transaction. A redelivered message id returns `{ duplicateMessage: true }`; the same id with another payload hash raises `InboxPayloadConflictError`. Added the `WagerTransactionRequested` envelope parser (`InvalidMessageError` for anything malformed).
- **Step 2 (commit `27d464e`).** `WagerMessageHandler` runs a message through the same use case and classifies the outcome (ack, retry, dead-letter) without throwing. `SqsConsumer` long-polls the FIFO queue, deletes a message only after the commit, retries through `ChangeMessageVisibility` with exponential backoff, and sends permanent errors to the DLQ with `ErrorCode` and `ErrorReason` attributes before deleting them. Messages of one wallet (one FIFO group) are handled in order; if one is not settled, the later ones of its group in the batch are released. Configuration through `SQS_CONSUMER*` variables; the consumer is switched off in tests.
- **Step 3 (uncommitted at the time of writing).** Graceful shutdown: `stop()` aborts the long poll, waits for the message being handled, releases the ones not started and, after `SQS_SHUTDOWN_TIMEOUT_MS`, hands back anything unfinished with visibility 0. Added `bun run poc:consumer` (AWS CLI, or the `amazon/aws-cli` image when `aws` is absent), the README "Queue consumer" section and `.env.example` entries. M7 is ticked in `PLAN.md` and M8 is marked current.
- Verification: full suite at the milestone close 486 pass, 0 fail (38 files, 53 s); typecheck clean. `sqs-consumer.test.ts` (16 tests) passed three consecutive runs. Two mutation checks failed the tests as expected: letting later messages of a group proceed after a failure, and skipping the hand-back at the shutdown timeout. `poc:consumer` ran against the live app: the BET applied once (balance 70.00), the duplicate left one inbox row, and the invalid message and the unknown wallet reached the DLQ as `InvalidMessageError` and `WalletNotFoundError`. ## Decisions and notes

- **Inbox (#51).** The row is written inside the use case's transaction, already processed, so it exists only if the business change committed. `ON CONFLICT DO NOTHING` because a unique violation aborts a PostgreSQL transaction (as in #26). Inbox deduplicates deliveries of one message; the idempotency key deduplicates the business operation across messages and HTTP.
- **Error classes (#52) and explicit dead-lettering (#53).** Business results are acknowledged. Transient and unknown errors are retried with a visibility delay, bounded by the redrive policy. Permanent errors are sent to the DLQ at once, because waiting for `maxReceiveCount` receives on input that can never succeed wastes work and blocks the wallet's group; if the send fails, the message stays and the redrive policy remains the fallback.
- **FIFO group and concurrency (#54, #55).** `MessageGroupId` is the wallet id. A failing message blocks its group until it succeeds or leaves; this is to be written in `ARCHITECTURE.md`.
- A first version of the shutdown code treated "not started" and "shutting down" as one flag, so a consumer driven by `pollOnce` released every message; the existing tests caught it and a separate `shuttingDown` flag fixed it.
- Known limits: messages released as group siblings still count as a receive; a receive aborted by `stop()` at the moment its response arrives leaves those messages hidden until their visibility timeout ends (none is lost); retry delays have a one-second granularity.
- The correlation id of a queue message is its message id; the envelope carries no separate field.
